① Why Redis Between Controller & Worker?

The controller could just inject IHubContext and broadcast directly. Routing through Redis pub/sub buys three things:

  • Decoupling from the request lifecycle — the HTTP request returns the instant the event is published; the slower fan-out happens off the request thread.
  • Horizontal scaling — see the next slide; this is the real payoff.
  • Single broadcast path — every event type flows through one worker, one place to log/handle/extend.
This is an application-level pub/sub, which is different from the official SignalR Redis backplane. Know the distinction — interviewers probe this.
HARD

① How It Scales Across Instances

Instance A  ─ worker subscribes "order-events"  ─ clients A1, A2
Instance B  ─ worker subscribes "order-events"  ─ clients B1, B2

Order placed on A:
  A publishes to Redis "order-events"
  Redis delivers to ALL subscribers (A's worker AND B's worker)
  A's worker → broadcasts to A1, A2   (its local IHubContext)
  B's worker → broadcasts to B1, B2   (its local IHubContext)
  → every client updates, no duplicates per client
Each client is connected to exactly one instance, and each instance broadcasts only to its own connections. Redis pub/sub fans the trigger out to every instance — so it behaves like a lightweight backplane for this app's events.
For a production multi-instance setup you'd still add the real AddStackExchangeRedis() SignalR backplane so framework concerns (groups, Clients.All across servers, sticky-session-free reconnects) work correctly. Our design handles the custom events; the backplane handles the SignalR plumbing.

② Why Is the Hub in Infrastructure, Not the API?

The brief put OrderHub in the API project. But the OrderEventWorker (Infrastructure) needs IHubContext<OrderHub> — it must reference the hub type.

API            ──references──►  Infrastructure
Infrastructure ──needs────────►  OrderHub (the type)

If OrderHub lived in API:
  Infrastructure ──would need──► API   ❌ circular reference
Moving OrderHub into Infrastructure breaks the cycle. The API still owns the route via app.MapHub<OrderHub>("/hubs/orders") — mapping only needs the type, which it already references.

Alternative I considered: define a broadcasting interface in Application, implement it in API, and inject it into the worker. That keeps the hub in API but adds indirection. For this size, relocating the hub is the cleaner call — and I can articulate both.

③ Scoped Services in a Singleton Worker

A BackgroundService is registered as a singleton. But DashboardStatsService depends on DbContext, which is scoped. You cannot inject a scoped service into a singleton — it would capture one DbContext for the app's lifetime (a classic captive dependency bug, and DbContext isn't thread-safe).

// Inside the worker, per message:
using var scope = _scopeFactory.CreateScope();
var stats = scope.ServiceProvider
    .GetRequiredService<IDashboardStatsService>();
await stats.GetCurrentStatsAsync(ct);
The worker injects IServiceScopeFactory and creates a fresh scope per broadcast, giving each message its own short-lived DbContext — safe and correct.
HARD

④ Worker Resilience & Host Lifetime

By default, if a BackgroundService throws an unhandled exception, the host's BackgroundServiceExceptionBehavior is StopHost — the whole app dies.

During docker compose up, the API can boot before Redis is ready. A naive SubscribeAsync would throw RedisConnectionException → host stops. I hit exactly this.

The fix

  • Wrap the subscription in a retry loop with exponential backoff (2s → capped at 30s), respecting the cancellation token.
  • Per-message handler is wrapped in try/catch and logs — a single malformed message never tears down the subscriber (there's a unit test for this).
  • Redis client configured with AbortOnConnectFail = false so it keeps retrying the connection.
HARD

⑤ One JSON Contract Everywhere

Three serialization boundaries must agree: controllers, SignalR payloads, and Redis cache/messages.

If they disagree, the enum OrderStatus.Pending serializes as 0 in one place and "Pending" in another. The React StatusBadge keys on the string — a number breaks it silently.
// JsonDefaults — shared by all three boundaries
PropertyNamingPolicy = CamelCase
Converters.Add(new JsonStringEnumConverter());
A single JsonDefaults.Options is reused for the API JSON options, AddJsonProtocol on SignalR, and Redis (de)serialization. Enums are always strings, names always camelCase — the client sees one consistent contract.

⑥ Two EF Core Gotchas I Hit

SQLite can't SUM a decimal

SQLite has no native decimal aggregate. SumAsync(o => o.TotalAmount) throws at runtime. Fix: pull today's amounts and sum in memory — a deliberate, documented client-side evaluation.

Mapperly can't run inside an EF projection

Calling a Mapperly method inside .Select(o => _mapper.ToSummary(o)) fails — EF can't translate an arbitrary method to SQL. Fix: .ToListAsync() first (materialize), then map in memory.

Both are about understanding the client-vs-server evaluation boundary in EF Core — a favourite interview topic.

🎤 Hard Interview Questions

Q: Why not call IHubContext straight from the controller?
It works for one instance, but it couples the broadcast to the request thread and doesn't scale. Routing through Redis lets the request return immediately and lets every API instance's worker broadcast to its own clients — the groundwork for horizontal scaling.
Q: Isn't this just the SignalR Redis backplane?
No — it's app-level pub/sub for my domain events. The official backplane handles SignalR's own cross-server plumbing (groups, Clients.All). In production I'd use both: the backplane for framework concerns, my channel for triggering domain broadcasts.
Q: How does a singleton background service use a scoped DbContext?
It can't inject one directly — that's a captive dependency and DbContext isn't thread-safe. I inject IServiceScopeFactory and create a fresh scope per message.
HARD

🎤 Hard Interview Questions (cont.)

Q: What happens if Redis is down when the app starts?
The worker retries the subscription with backoff instead of throwing — otherwise the default StopHost behavior would kill the app. The Redis client also uses AbortOnConnectFail=false.
Q: Is delivery guaranteed?
No. Redis pub/sub is fire-and-forget — if no subscriber is listening, the message is dropped. For at-least-once delivery and replay I'd move to Redis Streams or a broker like RabbitMQ.
Q: How do you keep the enum serialization consistent?
A single shared JsonSerializerOptions (camelCase + JsonStringEnumConverter) reused across controllers, the SignalR JSON protocol, and Redis. So OrderStatus is always "Pending", never 0.
Q: What would you improve with more time?
Concurrency-safe order numbering, durable messaging, the SignalR backplane for true multi-instance, and pushing computed stats inside the event payload to avoid a second DB read.
