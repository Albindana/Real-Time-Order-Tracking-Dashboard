Clean Architecture — 4 Layers

Each layer only depends on the ones "inside" it. Dependencies point inward.

🟦 API — entry point: HTTP controllers, Program.cs, middleware
🟩 Application — the "what": business logic, interfaces, DTOs, validators
🟨 Infrastructure — the "how": EF Core, Redis, JWT, SignalR hub, background worker
🟥 Domain — core business objects, zero dependencies
Why split it up? So business rules don't get tangled with database/framework details. You can swap SQLite → SQL Server without touching business logic, and unit-test against interfaces.

The Request → Real-Time Flow ⭐

This is the most important thing to understand. What happens when an order is placed:

1. Browser → POST /api/orders → OrdersController
2. Controller → OrderService.PlaceOrderAsync():
   • validates stock  • creates Order + Items (price snapshots)
   • decrements stock  • saves to DB  • refreshes Redis stats cache
   • PUBLISHES an event to the Redis "order-events" channel
3. Controller returns 201 Created — the HTTP request is now DONE
─────────── everything below runs off the request thread ───────────
4. OrderEventWorker (background service) is SUBSCRIBED to "order-events":
   • receives & deserializes the event
   • calls IHubContext to BROADCAST NewOrderPlaced + StatsUpdated
5. SignalR pushes to EVERY connected browser
6. React's connection.on(...) handlers fire → UI re-renders
The controller never talks to SignalR directly. It saves the order and drops a message in Redis. A separate worker does the broadcasting.

The hub is push-only — clients connect and listen, they never call server methods.

On the React side, useSignalR opens the connection and App.tsx registers a connection.on('EventName', ...) handler for each, updating React state.

How Authentication Works

  1. POST /api/auth/login with email + password.
  2. The API checks the password (ASP.NET Core Identity) and returns a JWT access token + a refresh token.
  3. The browser sends the token as Authorization: Bearer <token> on every call.
  4. [Authorize] rejects requests without a valid token; [Authorize(Roles="Admin")] requires the admin role.
Special case for SignalR: a WebSocket handshake can't send an Authorization header, so the client passes the token as ?access_token=... and the server reads it from the query string for hub connections.

The Roles of Redis

1. CACHE      key "dashboard:stats"
              → JSON of the current dashboard numbers
              → a new client gets data instantly, no DB query

2. PUB/SUB    channel "order-events"
              → the API publishes, the worker subscribes
              → the message bus that triggers broadcasts

3. COUNTER    key "dashboard:active-connections"
              → live count of connected clients

What the background worker is

OrderEventWorker is a BackgroundService (an IHostedService). It starts when the app boots and runs independently of any HTTP request. Its whole job: subscribe to the Redis channel and broadcast each message via SignalR.

🎤 Interview Questions

Q: Walk me through what happens when an order is placed.
The controller calls OrderService, which validates stock, saves the order via EF Core, refreshes the cached stats, and publishes an event to a Redis channel — then returns 201. Separately, a background worker subscribed to that channel receives the event and broadcasts it to all connected clients over SignalR.
Q: Why four layers?
Clean Architecture. Domain holds entities, Application holds logic + interfaces, Infrastructure holds technical implementations, API is the entry point. Dependencies point inward, so business logic doesn't depend on frameworks — testable and swappable.
Q: How does React receive live updates?
It opens a SignalR connection via the useSignalR hook and registers handlers like connection.on('NewOrderPlaced', ...). When the server broadcasts, the handler fires and updates React state, re-rendering the UI.

🎤 Interview Questions (cont.)

Q: How do you authenticate SignalR if WebSockets can't send headers?
The client passes the JWT as a query string access_token, and the bearer middleware is configured to read it from the query string for the hub path.
Q: Why DTOs instead of sending entities?
DTOs are flat shapes for the wire. Sending entities leaks internal fields, risks circular references (Order → Items → Order), and couples the API contract to the DB schema. DTOs give a stable, intentional contract.
Q: What does IHubContext do?
It lets code outside a hub — like the background worker — send messages to connected clients. IHubContext<OrderHub> is how other services broadcast.
